# 면접 예상 질문 전집 — MapleStory DX11 2D 엔진 포트폴리오

> 이 포트폴리오를 제출했을 때 받을 수 있는 질문을 카테고리별로 정리.
> 각 질문 아래 **[답변 포인트]**는 핵심 키워드 — 실제 답변은 본인 언어로 풀어서.

---

## A. 설계 결정 (프로젝트 전체)

**A1. 왜 STL을 안 쓰고 직접 구현했나요?**
[답변 포인트] 컨테이너/할당자/문자열의 내부 동작을 증명 가능한 수준으로 이해하는 것이 목표.
실제 게임 엔진(언리얼)도 자체 컨테이너를 쓰는 이유(할당자 통합, 메모리 추적, 캐시 배치 제어,
디버깅 용이성)를 직접 체감. std::vector와 TArray의 차이를 물으면 → 할당자 정책 주입,
POD memcpy 분기, RemoveAtSwap 같은 게임 특화 API.

**A2. 예외를 끈 이유는? 에러 처리는 어떻게?**
[답변 포인트] 게임 루프에서 예외는 비용(언와인드 테이블, 코드 크기)과 흐름 예측성 문제.
언리얼도 /EHs-c-. 대체: 프로그래밍 오류는 check/verify, 예상 가능한 실패는 TResult<T,E>
반환값, 복구 가능한 이상 상황은 ensure.

**A3. RTTI를 끄고 타입 판별은 어떻게 하나요?**
[답변 포인트] UClass 메타데이터 체인 + IsChildOf. dynamic_cast 대비: RTTI 데이터/문자열 비교
불필요, 얕은 체인에서 포인터 비교 몇 번. 제약: 단일 상속 전제 (엔진 계층에 충분).

**A4. 왜 언리얼 구조를 따라 만들었나요? 그냥 만들면 안 되나?**
[답변 포인트] 검증된 상용 엔진의 설계 결정을 "왜 그렇게 했는지"까지 역추적하며 배우는 것이
독자 설계보다 학습 밀도가 높음. 실무 투입 시 언리얼 코드베이스 적응력도 확보.

**A5. check / verify / ensure 세 개를 나눈 기준은?**
[답변 포인트] check=불변식(Shipping 제거, 부수효과 금지) / verify=항상 실행돼야 하는 호출
(Release에서도 평가) / ensure=복구 가능, 1회 보고 후 계속 진행. Release에서 check를 제거하는
건 핫패스 비용 때문(언리얼 Shipping 관례) — 대신 "check 안 부수효과 금지"를 규약으로 강제.
실제로 이 규약을 어겨 Release 전용 크래시를 겪고 규약화한 경험까지 말하면 강력.

## B. 메모리 / 할당자

**B1. FMallocBinned의 동작을 설명해보세요.**
[답변 포인트] 크기 클래스(16~512B) Bin, 64KB 정렬 페이지에서 블록 분할, 침습적 프리 리스트
O(1) 할당/해제. Free는 `ptr & ~(PAGE_SIZE-1)` 마스킹으로 페이지 헤더 역추적 → 블록별 헤더 0바이트.

**B2. 왜 페이지를 64KB로 '정렬'까지 시켰나요?**
[답변 포인트] 정렬돼 있어야 임의 포인터에서 마스킹 한 번으로 소속 페이지를 찾을 수 있음.
정렬이 없으면 포인터→페이지 매핑 테이블이 따로 필요.

**B3. 이 방식의 약점은? (꼬리 질문 대비)**
[답변 포인트] ① Bin 크기 반올림으로 내부 단편화(예: 33B 요청→64B 블록), ② 페이지 내 블록이
1개만 살아있어도 페이지 반납 불가, ③ 현재 단일 스레드 전제(락 없음) — UE는 스레드 캐시로 해결,
Phase 16+에서 필요 시 도입 예정이라고 답변.

**B4. 전역 operator new를 오버라이드할 때 주의할 점은?**
[답변 포인트] sized delete(C++14)까지 짝으로 오버라이드해야 함 — 컴파일러가 sized 버전을
우선 호출하므로 빠뜨리면 그 경로가 커스텀 할당자를 우회. new[]/delete[]도 짝 맞추기.
할당자 초기화 전 호출(전역 정적 생성자) 문제 → check(GMalloc)으로 조기 발견.

**B5. 내부 단편화와 외부 단편화의 차이는? 이 엔진은 각각 어떻게 대응하나요?**
[답변 포인트] 내부=블록 안 낭비(Bin 반올림, 감수), 외부=빈 조각이 흩어져 큰 할당 실패
(Bin 풀링으로 소형 할당을 페이지에 모아 제거).

**B6. alignment(정렬)는 왜 필요하고 어떻게 보장하나요?**
[답변 포인트] SIMD/원자 연산/타입 요구. FMemory::Malloc(size, alignment) 파라미터,
TArray는 alignof(T) 전달, 인라인 버퍼는 alignas(T). Bin은 시작 오프셋을 16의 배수로 설계.

## C. 컨테이너

**C1. TArray의 Add가 내부에서 하는 일을 순서대로 설명해보세요.**
[답변 포인트] 용량 확인→부족 시 ×2 성장(새 버퍼 Malloc→기존 원소 이전→구 버퍼 해제)→
placement new로 그 자리에 생성. 이전 시 POD면 memcpy, 아니면 move 생성+소멸자 (if constexpr).

**C2. placement new를 쓰는 이유는? delete는 왜 못 쓰나요?**
[답변 포인트] "메모리 확보"와 "객체 생성"의 분리 — capacity만큼 미리 확보하되 size만큼만
생성. delete는 소멸+해제가 묶여있어 불가 → 명시적 ~T() 호출 + FMemory::Free 분리.

**C3. TInlineAllocator는 어떻게 구현했나요? sizeof가 왜 안 커지나요(N=0일 때)?**
[답변 포인트] alignas(T) uint8 배열을 가진 베이스 클래스, m_pData가 내부 버퍼를 가리키면
인라인 상태. N=0 특수화는 빈 클래스 → EBO(빈 베이스 최적화)로 크기 기여 0.
이동 시 힙=포인터 탈취/인라인=원소 이동 두 갈래인 이유(내 버퍼는 남의 객체 안에 있음)까지.

**C4. TSparseArray는 왜 필요한가요? TArray로는 안 되나요?**
[답변 포인트] 해시 컨테이너가 원소를 "인덱스"로 가리키려면 삭제해도 인덱스가 안 변해야 함.
TArray는 RemoveAt이 뒤 원소를 당겨 인덱스가 깨짐. TSparseArray는 홀+프리 리스트로
인덱스 안정성과 O(1) 삭제/재사용을 동시에 확보.

**C5. TMap을 Open Addressing에서 체인 방식으로 바꾼 이유는?**
[답변 포인트] Open Addressing은 삭제 시 톰스톤(Deleted 표식)이 필수 → 추가/삭제 반복 시
톰스톤 누적으로 탐색 저하 + 불필요한 Rehash. 체인+TSparseArray는 삭제=unlink+슬롯 반납
O(1), 톰스톤 없음, Rehash도 버킷 재링크만(원소 무이동). 언리얼 실제 구조와 동일.
**직접 겪은 비교이므로 두 방식의 코드를 모두 구현해봤다고 말할 수 있음.**

**C6. 해시 충돌은 어떻게 처리하나요? 로드 팩터는?**
[답변 포인트] 같은 버킷의 원소들을 원소 내 m_HashNext 인덱스 체인으로 연결(separate
chaining의 인덱스 버전). 로드 팩터 1.0 초과 시 버킷 2배. pow2 유지 이유: 모듈로 대신
비트마스크(`hash & (N-1)`).

**C7. Rehash 때 원소를 안 옮긴다고요? 어떻게 가능하죠?**
[답변 포인트] 원소는 TSparseArray에 있고 버킷은 인덱스만 저장 → 새 버킷 배열을 만들어
전 원소를 순회하며 head 인덱스만 다시 꽂으면 끝. FString처럼 무거운 Value도 이동 비용 0.

**C8. begin/end 반복자에서 홀은 어떻게 건너뛰나요?**
[답변 포인트] 반복자가 m_bAllocated false인 슬롯을 skip하는 SkipToAllocated 루프.
++ 후에도 호출. end는 HighWater 위치.

## D. 문자열 / FName

**D1. FName이 뭐고 왜 필요한가요?**
[답변 포인트] 문자열 인터닝 — 같은 문자열을 풀에 한 번만 저장, 이후 uint32 인덱스로만 취급.
비교가 정수 비교 O(1) (문자열 길이 무관). 엔진에서 이름 비교가 매우 잦음(속성/태그/애셋).

**D2. FNamePool 등록 과정을 설명해보세요. 해시가 충돌하면?**
[답변 포인트] djb2 콘텐츠 해시 → 해시→인덱스 멀티맵에서 후보 조회 → 각 후보를 wcscmp로
실제 비교(충돌 안전망) → 없으면 신규 등록. 해시는 힌트일 뿐 최종 판정은 항상 문자열 비교.

**D3. FNameEntry에 문자열을 '인라인'으로 저장한 이유는?**
[답변 포인트] FString 보관 시 엔트리마다 별도 힙 버퍼+포인터 — 할당 2배, 캐시 미스,
포인터 기반 해시 위험. wchar_t[64] 인라인이면 엔트리당 할당 1회·연속 메모리.

**D4. 실제 언리얼 FName과 다른 점은? (꼬리 질문)**
[답변 포인트] UE는 대소문자 무시 비교(ComparisonIndex/DisplayIndex 분리)와 `_숫자` 접미사
(FName::Number) 지원. 현재는 대소문자 구분·접미사 없음 — 필요 시점(애셋 로딩)에 추가 계획.

## E. 스마트 포인터

**E1. TSharedPtr 컨트롤 블록 구조를 설명해보세요. 왜 카운트가 2개인가요?**
[답변 포인트] SharedCount(객체 수명)+WeakCount(블록 수명) 이원화. TWeakPtr는 객체 사후에도
"죽었는지" 물어봐야 하므로 블록이 더 오래 살아야 함.

**E2. WeakCount를 1로 초기화하는 이유는? (핵심 질문)**
[답변 포인트] 공유 소유자 그룹 전체의 암묵적 weak 참조. 마지막 shared 해제 시 Deleter가
도는 **도중에** 멤버 TWeakPtr들이 WeakCount를 반납해도 그룹 몫 1이 블록을 지켜줌.
이게 없으면 순환 참조 파괴 중 블록이 먼저 해제되는 이중 해제 발생 — **실제로 Release에서
힙 손상(0xC0000374)으로 겪고 std::shared_ptr와 같은 패턴으로 고친 경험** 스토리로 연결.

**E3. 순환 참조는 어떻게 해결하나요?**
[답변 포인트] 소유 방향은 TSharedPtr, 역방향은 TWeakPtr (보스→파츠 shared, 파츠→보스 weak).
weak는 카운트에 안 잡히므로 사이클이 안 생김. 사용 시 Pin()으로 일시 승격.

**E4. 참조 카운트를 원자적으로 만든 이유와 방법은?**
[답변 포인트] 두 스레드가 동시에 마지막 해제를 하면 이중 해제 — `--count == 0` 판정이
"감소 후 값"을 원자적으로 받아야 정확히 한 스레드만 0을 봄. MSVC _Interlocked/GCC __atomic
분기 래퍼. volatile은 원자성이 아니라 최적화 방지일 뿐이라는 구분도 언급.

**E5. MakeShared와 TSharedPtr(new T)의 차이는? (꼬리 질문)**
[답변 포인트] 표준/UE의 MakeShared는 객체+블록 단일 할당(캐시 지역성, 할당 1회).
현재 구현은 2회 할당 — 알고 있는 트레이드오프이며 개선 후보라고 답변.

## F. UObject / Cast

**F1. RTTI 없이 Cast<T>가 어떻게 동작하나요?**
[답변 포인트] DECLARE_CLASS가 클래스마다 정적 UClass(이름+부모 포인터)를 만들어 상속 체인
형성. 가상 GetClass()로 실제 타입의 UClass를 얻고 IsChildOf로 체인을 따라 부모 탐색 →
성공 시 static_cast. 실패 시 nullptr.

**F2. StaticClass()의 정적 변수를 함수 안에 둔 이유는?**
[답변 포인트] 함수-지역 정적(magic statics) — 최초 호출 시 생성이라 전역 초기화 순서
문제(SIOF) 없음 + C++11부터 스레드 안전 초기화 보장.

**F3. dynamic_cast 대비 장단점은?**
[답변 포인트] 장점: RTTI 데이터/문자열 비교 없음, 예측 가능한 비용(체인 깊이), /GR-로 바이너리
축소. 단점: 다중/가상 상속 미지원, 매크로 규약 강제 — 엔진 단일 상속 계층에선 문제 없음.

**F4. 실제 UE와 다른 점 아는 것 있나요? (정직함 테스트)**
[답변 포인트] ① UE는 UHT 코드 생성 + CDO + GC + 리플렉션 프로퍼티까지 있음(우리는 최소 골격).
② BeginPlay/Tick이 우리는 UObject에 있는데 UE는 AActor/Component 전용 — 인지하고 있고
분리 예정. 약점을 먼저 아는 모습이 오히려 신뢰를 줌.

## G. GAS (Gameplay Ability System)

**G1. GAS 구조를 설명해보세요.**
[답변 포인트] 정의(UGameplayEffect/UGameplayAbility)와 인스턴스 상태(ASC의 ActiveEffects/
ActiveTags/AttributeSet) 분리. 태그 기반 상호작용(차단/부여/제거).

**G2. 버프가 끝나면 스탯이 어떻게 원래대로 돌아가나요?**
[답변 포인트] Duration/Infinite 효과는 Base를 건드리지 않고, 매 변화 시 Current=Base에서
활성 효과 전체를 Add→Multiply→Override 3패스로 재계산 — 효과가 목록에서 빠지면 자동 원복.
Instant/Period(도트)만 Base 직접 수정(영구).

**G3. 쿨다운은 어떻게 구현했나요?**
[답변 포인트] 별도 시스템 없음 — CooldownEffect(Duration)가 `Cooldown.X` 태그를 부여하고,
스킬의 ActivationBlockedTags에 그 태그가 있어 재발동 차단. 만료 시 태그 자동 제거.
언리얼 GAS와 동일한 태그 주도 설계.

**G4. 독 도트 1초마다 데미지는 어떻게 동작하나요?**
[답변 포인트] Duration 효과 + Period=1. Tick에서 PeriodTimer 차감, 0 이하마다 Modifier를
Base에 적용 후 타이머 +Period(드리프트 방지).

## H. C++ 언어 심화 (구현 중 실제 사용한 것들)

**H1. if constexpr와 일반 if의 차이는? 어디에 썼나요?**
[답변 포인트] 컴파일 타임 분기 — 선택 안 된 가지는 인스턴스화 자체가 안 됨.
TArray/TSparseArray의 POD memcpy vs move+destroy 분기.

**H2. 이동 의미론(move semantics)을 어디에 어떻게 적용했나요?**
[답변 포인트] MoveTemp(=std::move 자체 구현), 컨테이너 성장 시 원소 이전, FString/TArray
이동 생성자(포인터 탈취+원본 무력화), TMap::Add(Key&&, Value&&) 오버로드.

**H3. copy elision / RVO를 설명해보세요.**
[답변 포인트] 함수가 값 반환 시 임시를 호출자 자리에 직접 생성. C++17부터 prvalue 반환은
guaranteed. **MSVC Debug에서 초소형 인라인 함수의 반환값 처리 코드생성이 어긋나는 실버그를
만나 noinline으로 격리 해결한 경험**과 연결하면 최고의 답변.

**H4. volatile과 atomic의 차이는?**
[답변 포인트] volatile=컴파일러 최적화/재배치 방지일 뿐 원자성·가시성 보장 없음.
원자성은 인터락 명령(lock xadd 등) 필요 — 그래서 _Interlocked/__atomic 인트린식 사용.

**H5. EBO(빈 베이스 최적화)가 뭔가요?**
[답변 포인트] 빈 클래스를 베이스로 상속하면 크기 기여 0. TInlineAllocator N=0 특수화가
빈 클래스라 기본 TArray 크기가 안 커지는 근거.

**H6. NDEBUG와 assert의 관계, 그리고 함정은?**
[답변 포인트] NDEBUG 정의 시 assert는 ((void)0) — **표현식 미평가**. assert 안 부수효과는
Release에서 코드가 사라짐. 실제로 이걸로 Release 전용 크래시를 만들고 잡은 경험 →
"구성별로 코드가 달라지는 매크로에 부수효과 금지"를 규약화.

## I. 디버깅 경험 (반드시 나올 질문)

**I1. "이 프로젝트에서 가장 어려웠던 버그는 뭐였나요?"**
3개 준비 (STAR 구조: 증상→가설/배제→확정 근거→해결→교훈):

1. **MSVC Debug 인라인 코드생성 버그** — 코드를 3번 바꿔도 크래시가 1비트도 동일 +
   콜스택에 해당 함수 프레임 부재 → "수정이 생성 코드에 반영 안 됨" 추론 → noinline
   out-of-line 분리로 해결. 컴파일러도 틀릴 수 있다는 것과 그때의 증명 방법.
2. **Release 전용 이중 해제(순환 참조)** — Debug 힙의 0xDD 채움이 버그를 감춤 →
   Debug/Release 힙 차이 지식 + 암묵적 weak 참조 패턴으로 해결.
3. **check() 부수효과 증발** — 크래시 주소(0x14)를 슬롯 오프셋 계산과 대조해 원인 확정.
   진단용 계측을 커밋에 남기며 이분 탐색한 과정.

**I2. "재현이 안 되는 버그는 어떻게 접근하나요?"**
[답변 포인트] 구성 차이(Debug/Release, RTC, 할당자)를 하나씩 고정하며 이분 탐색,
가설마다 "이걸 바꿨는데 증상이 안 변하면 무죄" 원칙, 크래시 주소를 자료구조 레이아웃과
대조해 수치로 확정. 위 사례들이 전부 실례.

**I3. "테스트는 어떻게 했나요?"**
[답변 포인트] Phase마다 단위 테스트 선작성(86개), Debug/Release 양쪽 필수,
추가로 Linux g++ 3구성+valgrind로 컴파일러/힙을 바꿔 이중 검증. MSVC에서 안 잡히는
문제가 valgrind에서(또는 그 반대로) 잡힌 실례 보유.

## J. 약점 방어 / 꼬리 질문 대비

**J1. "단일 스레드 전제네요? 멀티스레드는요?"**
[답변] 참조 카운트만 선제적으로 원자화(Phase 16+ 병렬 대비). 할당자/컨테이너는 의도적으로
단일 스레드 — 필요 시점에 스레드 로컬 캐시(할당자), 락/lock-free(컨테이너) 도입 계획.
"필요 전에 복잡도를 사지 않는다"는 판단 근거 제시.

**J2. "TMap을 TSet<TPair>로 안 만든 이유는?" (UE를 아는 면접관)**
[답변] KeyFuncs 추상화 계층 없이 두 컨테이너를 병렬 구현하는 쪽이 각각의 코드가 자명해짐.
자료구조 골격(TSparseArray+체인)은 동일하며, 통합은 인지된 리팩터 후보.

**J3. "렌더링이 아직 없는데요?"**
[답변] 로드맵상 LAYER 1(코어) 완료 시점. 코어를 먼저 완성한 이유: 상위 시스템 전부가
컨테이너/메모리/오브젝트 모델 위에 서므로 기반 품질이 전체를 결정. Phase 8(DX11) 착수 예정
— DXDevice/SwapChain/SpriteBatch/RenderQueue 설계안까지 준비돼 있음.

**J4. "성능 측정은 해봤나요?"**
[답변] FName 등록 1000개 벤치(선형 대비), 처닝 테스트로 톰스톤 제거 효과 확인.
본격 프로파일링은 렌더러+실게임 루프가 생기는 Phase 8 이후 실부하로 진행 예정 —
마이크로벤치보다 실워크로드 측정이 의미 있다는 입장.

**J5. "AI(Claude 등) 도움을 받았나요?" (요즘 자주 나옴)**
[답변 포인트] 사용했다면 솔직하게 + **본인이 설계 결정과 디버깅 판단의 주체**였음을 구체
사례로 증명 (왜 이 구조를 택했는지, 버그 원인을 어떻게 확정했는지를 막힘없이 설명하는 것이
최선의 답). 이 문서의 모든 질문에 스스로 답할 수 있게 준비하는 것이 곧 방어.
